## Supported guest isolation does not include every host allocation

[Microsoft isolation modes](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container) distinguishes shared-kernel process isolation from Hyper-V isolation with a separate guest kernel. Host volumes, named pipes, network namespaces/ports and devices are explicitly documented ways to pierce that boundary. A future closed topology must enumerate every permitted crossing and the authority behind it, not assume isolation from an option name.

[Container resource controls](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/resource-controls) maps Hyper-V memory controls to VM memory and CPU limits to the hypervisor, in addition to guest job controls. This supports a guest-domain memory-cap candidate. The description is high-level and implementation-dependent, not an actual current-host readback or an exact peak host allocation contract. Its storage table links job I/O-rate controls: it cannot override the earlier documented unsupported-version caveat or convert a rate into cumulative storage/node quota.

[Hyper-V memory performance](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/role/hyper-v-server/memory-performance) separately requires root-partition memory for I/O virtualization, snapshots and management. Therefore a guest memory cap cannot be counted as a cap on all host services, kernel allocations and I/O buffers caused by that guest. This research finds no exact complete host-domain hardcap in these pages; it does not prove no supported mechanism can exist.

The [HCS schema](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference) exposes VirtualMachine_Memory.SizeInMB and AllowOvercommit. Enabled overcommit uses host pagefile backing instead of static physical backing. Deferred commit, page size and device/cache configuration are additional distinct fields. StorageQoS is operations/second and bytes/second, not retained-object storage. An eventual whole literal configuration must freeze every supported memory/backing/device/cache field and prohibit unauthorized expansion. [HcsModifyComputeSystem](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcsmodifycomputesystem) permits memory and device/share changes; immutable initial JSON alone does not prevent later authorized-host mutations. No configuration or HCS API was invoked.

## Storage must include every backing and lifetime

[Container storage](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-storage) describes per-container scratch and a compatibility-oriented virtual free-size setting. Those descriptions do not alone establish exact retained bytes, live/pending/deleted-open node counts, complete backing allocations or provider/cache lifetimes. Layer storage and bind/volume mappings are distinct domains. No StorageSandboxSize or docker option is admitted as the complete required quota.

[Hyper-V storage](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/role/hyper-v-server/storage-io-performance) documents guest, host virtualization, host storage and physical-disk stages. Fixed virtual disks allocate backing when created, while dynamic/differencing disks allocate on demand. A fixed-disk candidate may bound its own provisioned disk extent only after exact geometry/metadata/expansion controls are established; it does not bound all separate snapshots, state/log files, image layers, external mapped volumes, host cache or live-object counts. No disk/image was acquired, created, attached, resized, parsed or deleted. No file-count bound is invented from disk size.
