## A distinct physical allocation mechanism

The [official untyped tutorial](https://docs.sel4.systems/Tutorials/untyped.html) describes a static kernel allocation and root-task boot objects, with remaining physical memory exposed as sized untyped capabilities. Retyping consumes a subset of the original region. Device untyped differs from normal RAM. BootInfo describes physical location, size and device status. Watermark allocation includes alignment waste; those bytes are unavailable until the relevant children are revoked. This supports investigating explicitly partitioned physical allocation, rather than inferring all-host limits from process memory counters. It is not a complete selected-system proof.

The [API reference](https://docs.sel4.systems/projects/sel4/api-doc.html) documents Retype failing when requested objects exceed available space, and limits object creation by destination slots and configured fanout. Revoke deletes child capabilities and reports success or error. The documented logical result does not supply this project's complete driver/device/broker shutdown or a numeric worst-case teardown deadline. No such guarantee is inferred from a successful return or a finite slot count.

## Proof coverage and guest compatibility must match the topology

The [verification assumptions](https://sel4.systems/Verification/assumptions.html) separate hardware, assembly, boot, machine-interface and DMA assumptions. The [official FAQ](https://sel4.systems/About/FAQ.html) treats DMA hardware and drivers as requiring independent assurance, and distinguishes unverified IOMMU/VT-d configurations. A capability to ordinary memory cannot by itself attest an external device's quiescence or prevent an unproven DMA write. No driver correctness or hardware assumption is asserted for this host.

The [verified configurations](https://docs.sel4.systems/projects/sel4/verified-configurations.html) page explicitly distinguishes architecture and enabled features; its X64 verified configuration excludes VT-x/hypervisor mode. Boot and device address translation are excluded from the listed verified configurations. Do not transfer a verified baseline's properties to a differently configured x86 VMM or claim all configurations unsafe.

[CAmkES VMM documentation](https://docs.sel4.systems/projects/camkes-vm/) describes Linux guest projects and platform-specific feature matrices, with separate guest images, driver components, shared connectors and passthrough storage examples. These examples establish neither a supported Windows guest for our exact x64 CPython/native wheels nor complete cross-OS qualification. A missing Windows match in this page is not proof of impossibility. The documented examples do not select a current guest image or establish our source/archive/ABI/installed-form closure.
