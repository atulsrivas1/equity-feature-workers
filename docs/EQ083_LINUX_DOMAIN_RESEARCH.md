## Supported controls and their documented limits

[Cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) tracks major user, cache and kernel memory, including secondary page tables for KVM on specified architectures. It explicitly qualifies coverage as not completely watertight. memory.max is a hard-limit/reclaim/OOM mechanism whose usage can temporarily exceed the setting. Memory stays charged to its originating cgroup after process migration. Swap, zswap and HugeTLB have distinct controls/accounting caveats. pids.max constrains fork/clone; administrative attachment can exceed it. cgroup.kill handles concurrent fork/migration but its request does not establish bounded resource reclamation. populated0 means no live processes. Deleted cgroups may remain dying and consume resources for an undefined period. These are scoped contracts, not instantaneous all-host byte or completed-cleanup proof.

[Tmpfs](https://docs.kernel.org/filesystems/tmpfs.html) exposes limits for allocated blocks and inodes; zero means unlimited. Limits can change on remount. Backing can include swap and memory, and metadata/extended-attribute usage matters. A tmpfs limit is a filesystem-domain primitive, not a bound on every host allocation, outside writer or cumulative application-write count. Page-rounded charged data, inode/context lifetime and deleted-open objects need exact supported coverage. No mount/remount or memory/swap operation was performed.

[KVM's userspace-memory API](https://docs.kernel.org/virt/kvm/api.html) maps guest memory regions to userspace backing and permits region changes. Guest-visible memory size therefore needs actual immutable controller authority over backing, devices and later modifications. It is not independently a bound on all host cache, kernel, IPC, worker or external storage resources. No KVM ioctl or VM process was invoked; no guest image was acquired.
