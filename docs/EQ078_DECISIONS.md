## Committed receipt, cancellation and authorization

Actual accepted native commands checks cancellation after publish/verify_receipt and before readback. A registered guarded sink retains the exact envelope, receipt and encoded result bytes at commit. It never rolls back or relabels a committed receipt. Public cancel after a verified terminal success is idempotent and leaves success. If cancellation wins before native verified readback, job becomes cancel_requested until actual execute_plan exits, then cancelled; a captured committed receipt remains an internal historical fact without a visible result ID. Same owner/key retry returns this same terminal job, never another execution. Native readback failure after commit is failed with typed redacted error and captured receipt retained. No special cancellation token hides cancellation after commit.

Sink begin/write/commit/lookup/read are guarded by current original owner/grant/policy/dataset/config rights. Commit and visible terminal-state update share the ledger's revocation lock for their own boundaries; no lock spans expensive acquisition/calculation. Authorization immediately before native commit prevents publication if revocation wins first. If commit wins and revocation wins before readback/visibility, retain the historical receipt and deny readback/output; never claim rollback or expose a post-revoke result. Abort/cleanup must remain callable by the trusted execution owner after revocation, returning the actual committed state when appropriate. Cancellation/revocation may not drain foreign completions. Wrapper storage and sink lifetime remain creating-thread owned; HTTP uses synchronized immutable snapshots only. Every source chunk verifies current rights and full original source/receipt/content. Native logical rows/bytes/cooperative timeout are not hard CPU/RSS preemption.

## Finite startup and retention profile

One shared process-owned scheduler: one actual running globally/per principal, one queued per principal, two queued globally. Max16 command registrations,16 job records globally/eight per principal, each record's canonical metadata bounded8192bytes; startup denies nonfinite/excess settings. Metadata contains opaque IDs/digests/state/fixed errors and accounting, no source rows/config paths/credentials. Reserve record, queue and262144 retained-output bytes atomically per admitted job. This is a tighter owned job profile within accepted1MiB per-principal/2MiB global retained-result caps. Reservations persist across interval resets/controllers/retries and until actual release; queued cancellation/failure releases output reservation once, but retains idempotency record. Record metadata has its own finite131072byte global budget; count actual encoded lengths, reject oversize metadata before source execution.

Within the262144byte per-job reservation, encoded native result bytes are capped65536, canonical retained wire result bytes131072 and combined encoded envelope/receipt bytes32768. Count complete native encode_result bytes (including quality/evidence), complete original producer wire payload bytes, encode_envelope/encode_receipt bytes and any retained duplicate copies; their aggregate must also fit262144. Do not count just feature values or ignore JSON precision expansion. Store immutable encoded forms rather than extra native/result clones after worker exit. No result download is advertised in EQ078; EQ079 must independently qualify retrieval/physical expiry/precision. All successful or committed-but-cancelled/failed retained payloads expire at min(completion+300seconds, original grant expiry), even if no HTTP poll occurs. Explicit scheduler sweep and admission/status operations perform cleanup; tests must prove actual payload removal, not logical expiry alone. Running native objects/reservations remain held until real native exit even after deadline/revocation.

Job grants have explicit calculate/job_manage/retain rights and a finite validity interval at most3600seconds; this restricts new job grants without extending old slice grants. Rights/effective clock use trusted server ns, with exact half-open expiry; deadline uses a monotonic server clock independent of client/numerical timestamps. Store paired start/deadline, reject backward/nonfinite clock observations rather than replenish budgets. Terminal records/idempotency tombstones persist until original job grant expiry; after result TTL an authorized identical retry returns the original expired job, not new work. Tombstone purge requires expiry of the original grant, which cannot authorize another execution; renewed grants require a new revision and constitute new admission. Never evict a live tombstone to make capacity: deny new jobs when16/eight limits are reached. Unknown/foreign/purged IDs deny without disclosure.

Initial scheduler state is in memory and has no durable restart recovery claim. A restarted instance has a new opaque epoch in job IDs; old jobs/receipts are unavailable, and clients must not automatically retry old commands across a new epoch. Until durable recovery is separately qualified, startup/operations must explicitly document this restriction and the client must enforce epoch discovery when async retries are added. A same-process transport retry is idempotent; a restart is not represented as the same surviving job. EQ083/084 must qualify recovery requirements before hosted acceptance. No stable or production resilience claim.
