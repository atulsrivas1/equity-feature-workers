Canonical [EQ064#72](https://github.com/atulsrivas1/equity-features/issues/72), E08/R5. Dependencies EQ057–063 and R4.1 accepted; one active story. 13 provisional complexity points, not days. Planned experimental workers0.1.0a9; no implementation or qualification claimed by this plan.

## Identity, mathematics and timing

No numerical formula, data units, market/knowledge cutoff, warm-up, coverage, algorithm, Task/Output/Result/Receipt schema or mandatory dependency change. Existing Task/Output codecs and GenerationSpec/GenerationStore are the authority for exact expected generation membership and actual sink receipt/full result readback. Operational catalog acceptance records a caller's generation selection; it does not authenticate source facts, admit a private pilot or establish mathematical correctness.

Catalog key SHA256 binds versioned domain plus canonical [namespace,job_id]. Every entry contains the existing complete ordered OutputManifest population and reconstructs an exact GenerationSpec from their tasks. Namespace/job must match every entry; generation IDs are distinct. Entry ordinal is its one-based position, sequence=count(entries), selected=last entry. Units are integer counts, not seconds or UTC time; no hidden clock/timestamps. Supersession is an append in retained history, never silent replacement of older generation identities.

Canonical ASCII JSON, sorted keys, compact separators, no NaN/duplicate/unknown fields. Version efworker-catalog1. One bounded JSON record per catalog combines selected pointer and complete ordered history, so no split pointer/history transaction. Existing output codecs embed Task/config/revision/cutoff/receipt identities, preserving exact bytes and original receipts. Snapshot identity is a domain-separated SHA256 of its canonical bytes. Validation reconstructs all entries/specs and demands canonical byte equality/key binding, exact positive sequence/population, no duplicate generation/tasks within an entry and committed original receipts. Catalog schema is operational metadata, not a second sink protocol.

## API and selection state machine

Proposed typed public CatalogLimits, CatalogEntry, CatalogSnapshot, CatalogOutcome and CatalogStore. Constructor accepts caller-owned root/limits/requirements/protected sources and performs no writes. Trusted local Windows/Linux only, namespace .efworker-catalog1. Root/owned-file symlinks/UNC/source overlap rejected; callers own mount truth/security and retain stable lock files.

snapshot(namespace,job_id) is read-only: missing yields None; otherwise bounded open/read/close/validate returns immutable full metadata snapshot. It never mkdirs/writes/creates locks, discovers source storage, starts callbacks or opens a writer database. A metadata snapshot alone is not an accepted usable result.

verify(snapshot,generations,dependencies) is read-only and proves snapshot history is an exact prefix of the currently recorded history, then GenerationStore.read verifies its selected immutable complete generation using exact caller-supplied dependencies, actual SDK sink lookup/original receipt/full logical result/entity readback. An older snapshot can continue reading its original generation after later selections append, as long as that generation still verifies. Forged, truncated or conflicting lineage fails; missing/staged/unknown/corrupt/busy backend state cannot become an accepted read. CatalogOutcome.accepted requires a verified complete GenerationOutcome and a recorded snapshot; contains original outputs/barrier results. No unqualified file-presence inference or deserialization of executable objects.

select(spec,generations,dependencies,expected_sequence,cancellation=None) is creating-thread owned and one bounded pass. A stable nonblocking global catalog writer lock serializes ONLY catalog metadata acceptance. All sink publication remains with existing SerialPublisher/backend locks; catalog selection performs no sink begin/write/commit and never enables multiple worker writers to one DuckDB database. Validate caller/config/cancellation before side effects. Under writer lock, read current snapshot and check expected_sequence against current sequence before new selection; integer exact/nonnegative (bool rejected). First accepted generation requires0 and appends sequence1. Same currently selected exact generation is idempotent (original snapshot/sequence), but still re-verifies actual generation/output bytes before returning accepted. A stale different generation conflicts. Re-selecting an older historical generation is rejected; a correction uses a new generation identity with explicit append. Retained historical identity/output conflict is never overwritten.

Only an already published immutable GenerationStore record plus live verified receipt/result readback permits selection. Incomplete/absent/staged/unknown/BUSY generation returns unaccepted outcome without pointer/history change; corruption/conflict/invalid input fails typed and preserves prior state. Cancellation before replacement leaves prior selected state; cancellation after actual replacement cannot retract acceptance. Re-entry rejected; writer release failures normalized to fixed UNAVAILABLE and cannot leak private exception text. Caller can snapshot/verify after uncertain replacement/release to determine durable current state; no exactly-once distributed transaction claim.

Write an exclusive UUID stage file in the same catalog directory, flush/fsync, check cancellation, then os.replace ONE canonical catalog file. Retain interrupted stages; never remove old generations, stages, lock files or foreign files. Only the complete catalog file is visible to readers. No recursive cleanup, network-filesystem/power-loss/adversarial-mutation durability or hard RSS guarantee.

## Live readers and resource limits

Normal snapshot readers close the file before logical validation/actual backend readback. They retain immutable snapshot objects, not live catalog file handles, during feature consumption. Same-directory replacement can fail while Windows readers retain an incompatible live handle: return fixed BUSY on local Windows sharing/access-denied replacement, preserve original pointer/history and complete stage; caller retries explicitly after reader closes. Other OS failures are fixed UNAVAILABLE. Linux reader can keep old inode bytes when a replacement succeeds. Both outcomes must be tested natively, never assumed from metadata flags or generalized to remote filesystems. Existing sink readers can be BUSY under foreign DuckDB ownership; select/verify return no accepted result until actual readback succeeds, preserving catalog state.

Defaults:64 catalogs,64 retained selections per catalog,8MiB aggregate active catalog bytes,4MiB per catalog record,4096 maximum limits for catalogs/history. All counts exact positive integers. Bound inventory incrementally; recognize only stable writer.lock, SHA256.catalog.json and UUID stage files; unknown directories/files/symlinks fail closed. History full means RESOURCE_LIMIT, no truncation/eviction. Stages retained outside active-byte accounting; logical quotas do not limit cumulative interrupted disk/native RSS. Barrier limits still bound actual dependency/result readback. Cross-catalog active count/byte updates remain within the same writer lock. Different namespace/jobs are isolated identities with common bounded serialized metadata acceptance.
