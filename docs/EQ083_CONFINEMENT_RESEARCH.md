## Process handles and object security

[Microsoft process rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights) documents an explicit security descriptor at process creation and DACL checks for OpenProcess. PROCESS_DUP_HANDLE permits duplication and can expose additional process authority through a duplicated pseudo handle. [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) requires that right on source and target process handles; duplicated file handles refer to the same object. Thus excluding unrelated writers must cover access to the controller/provider/children's process objects and existing process/object handles, not just file opens or a PID list.

[Object ownership](https://learn.microsoft.com/en-us/windows/win32/secauthz/owner-of-a-new-object) normally grants implicit WRITE_DAC. The [OWNER RIGHTS SID S-1-3-4](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers) has documented ACE semantics suppressing implicit owner READ_CONTROL/WRITE_DAC. Therefore owner rights are not inherently impossible to restrict. This source lists Windows Server versions: it is a documented primitive, not current-host applicability or an inspected native access check. Separate explicit grants, privileges, existing handles and all relevant object descriptors still need closure. No actual ACL or owner was changed. No opaque same-user name or private package SID is sufficient proof by itself.

A future integrated transaction must supply and retain the complete process/thread/job/root/provider object security policy BEFORE any untrusted execution, and establish actual token privileges and ownership. It must prevent acquisition or transfer of authority through duplication, inheritance, broker paths and preexisting handles across every relevant process instance. Existing fixed HANDLE_LIST controls launch inheritance only; it does not certify this complete policy. ## AppContainer access and writable profile locations

[The official launch contract](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) describes intersecting user/group and package/capability permissions. LPAC opts out of broad All Application Packages access and requires explicit capabilities for additional resources. This is a supported access-control model, not an exact process-instance allowlist or universal storage quota.

The same launch contract creates accessible profile storage and redirects LOCALAPPDATA/TEMP/TMP to it. A grant on the custom quota root therefore does not establish that it is the only writable root. Setting environment variables does not revoke native access to the actual profile or inherited handles. Choosing LPAC without a complete profile/registry/IPC/broker/device/capability policy also does not establish closure. No AppContainer/LPAC profile was created, reused, deleted, redirected or changed. No host inventory, registry, token, native API or ACL operation was run.

Before selecting a topology, identify every writable resource class and real identity: quota volume, profile/temp, registry, named objects, IPC/device handles, inherited/duplicated sections/files and provider queues. Freeze supported denial or bounded backing for every permitted path and any broker that can write for the child. Unsupported or unknown paths deny admission. Security descriptor checks on process objects and storage accounting are complementary; neither substitutes for the other. AppContainer plus a closed process DACL ALONE is not established as a complete boundary by these documentation reads.
